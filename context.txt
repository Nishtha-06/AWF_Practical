PRACTICAL 5
-----------

Objective/functionality:

- Add the Node.js backend, Express task routes, MongoDB connection through
	Mongoose, a Task model, request logging, and an error-handler module.
- The PR5 commit added all backend files and backend package metadata.

Backend setup:

- Backend entry point: `backend/server.js`.
- Backend package type is not declared in `backend/package.json`, so the code
	uses CommonJS `require`/`module.exports`.
- Backend dependencies are `cors`, `dotenv`, `express`, and `mongoose`.
- `backend/package.json` has no `scripts` section. No backend start or dev
	command is defined there.
- The backend source uses port `3000` in `server.js`. The supplied Practical 6
	handout mentions port `5000`, but the actual current code uses `3000`.

Server behavior in `backend/server.js`:

- Loads environment variables with `require("dotenv").config()`.
- Imports `connectDB` from `./config/db` and calls `connectDB()` before
	registering the routes/listening callback.
- Creates an Express app and sets `const PORT = 3000`.
- Registers `express.json()` for JSON request bodies.
- Registers `middleware/logger.js`.
- Mounts `routes/tasks.js` at `/tasks`.
- Starts listening on port 3000 and logs `Server running on port 3000`.
- Imports `cors`, but the current code does not call `app.use(cors())` or any
	other CORS configuration. The comment says it should allow the React
	frontend to communicate, but the middleware is not actually registered.
- Imports no `errorHandler` in the current file and does not register
	`app.use(errorHandler)`. Route errors are forwarded with `next(error)`, but
	the intended custom handler is therefore not currently connected.

Database configuration:

- Connection file: `backend/config/db.js`.
- Mongoose is imported and `mongoose.connect(process.env.MONGO_URI)` is called
	inside an async `connectDB` function.
- On success it logs `MongoDB connected successfully`.
- On failure it logs the error message and calls `process.exit(1)`.
- Environment variable name: `MONGO_URI`.
- The repository `.env` contains a local MongoDB URI whose database name is
	`task_management`. The value is intentionally not copied here.
- The configured URI format is a local MongoDB address (`mongodb://127.0.0.1`)
	with the database path `task_management`.
- Whether MongoDB is actually running and whether the connection succeeds has
	not been verified from the repository alone.

Middleware:

- `backend/middleware/logger.js` logs the HTTP method, request URL, and local
	date/time, then calls `next()`.
- `backend/middleware/errorHandler.js` logs `err.stack` and returns status 500
	with `{ "message": "Internal Server Error" }`. It exists in the repository
	but is not mounted by `server.js`.

Task model in `backend/models/Task.js`:

- Mongoose model name: `Task`.
- Collection naming is left to Mongoose's normal model-to-collection behavior;
	an explicit collection name is not configured in the schema.
- `title`: String, required.
- `description`: String, required.
- `completed`: Boolean, optional, default `false`.
- `createdAt`: Date, optional, default `Date.now`.
- No timestamps option is enabled, so there is no automatic `updatedAt` field.
- No custom validators, trimming, length rules, enum, or default for title or
	description are defined.

Task routes in `backend/routes/tasks.js`:

- GET `/tasks`
	- Calls `Task.find()`.
	- Returns status 200 with the array of task documents as JSON.
	- Forwards database errors to `next(error)`.

- POST `/tasks`
	- Passes `req.body` directly to `Task.create(req.body)`.
	- Returns status 201 with the created task document as JSON.
	- Mongoose required-field/schema errors are forwarded to `next(error)`.
	- No route-level request-body validation is defined beyond the model.

- PUT `/tasks/:id`
	- Uses `Task.findByIdAndUpdate(req.params.id, req.body, { new: true,
		runValidators: true })`.
	- Returns status 200 with the updated task document.
	- Returns status 404 with `{ message: "Task not found" }` if no document
		matches the id.
	- Runs Mongoose validators during the update.
	- Other errors, including malformed ids, are forwarded to `next(error)`.

- DELETE `/tasks/:id`
	- Uses `Task.findByIdAndDelete(req.params.id)`.
	- Returns status 200 with `{ message: "Task deleted successfully" }` when a
		document is deleted.
	- Returns status 404 with `{ message: "Task not found" }` if no document
		matches the id.
	- Other errors are forwarded to `next(error)`.

CURRENT PRACTICAL 6 IMPLEMENTATION
===================================

Intended architecture:

React frontend (`localhost:5173` by the Vite default)
		-> fetch
Node + Express backend (`localhost:5000` in the handout, but `3000` here)
		-> Mongoose
MongoDB

The actual code currently uses port 3000 for both the backend server and the
frontend API base URL. Vite has no explicit `server.port` setting in
`pr1/vite.config.js`, so its normal development default is 5173. The backend
port must therefore be treated as 3000 unless changed in source.

Frontend entry and routing:

- `pr1/src/main.jsx` mounts the React app inside `StrictMode` and
	`BrowserRouter`.
- `pr1/src/App.jsx` currently defines `/`, `/projects`, and `/contact`.
- `/projects` is the current integration surface for tasks.

Frontend API layer in `pr1/src/api.jsx`:

- `BASE_URL` is exactly `http://localhost:3000`.
- `getTasks()` sends GET `http://localhost:3000/tasks`, throws
	`Failed to fetch tasks` for a non-2xx response, and returns parsed JSON.
- `createTask(task)` sends POST `/tasks` with JSON content type and
	`JSON.stringify(task)`, throws `Failed to create task` for a non-2xx response,
	and returns parsed JSON.
- `updateTask(id, task)` sends PUT `/tasks/:id` with JSON content type and the
	serialized task body, throws `Failed to update task` for a non-2xx response,
	and returns parsed JSON.
- `deleteTask(id)` sends DELETE `/tasks/:id`, throws `Failed to delete task`
	for a non-2xx response, and returns parsed JSON.
- The names are consistent in this file: `getTasks`, `createTask`,
	`updateTask`, and `deleteTask`. No `getTask` or `BASE_ULR` typo was found.
- These helpers do not set a credentials option and do not parse server error
	bodies before throwing their generic errors.

Current task UI in `pr1/src/pages/Projects.jsx`:

- State currently includes `tasks` (initially `[]`), `loading` (initially
	`true`), and `error` (initially `false`).
- An empty-dependency `useEffect` calls `getTasks()` once when the page mounts.
- Success stores the returned array and sets loading false.
- Failure sets error true and loading false.
- While loading, it renders `Spinner`.
- On failure, it renders `ErrorMessage`.
- On success, it renders `Tasks`, an empty-state `No tasks found.`, or a list
	using `_id`, `title`, `description`, and `completed`.
- The UI does not currently render a create form, edit control, delete
	control, completed toggle, or buttons calling `createTask`, `updateTask`, or
	`deleteTask`.
- The API helpers for POST, PUT, and DELETE are implemented in code but are not
	imported or called by the current Projects page.

CURRENT PRACTICAL 6 PROBLEMS AND NEXT ACTIONS
---------------------------------------------

1. Problem: CORS is not enabled in the backend.
	 Evidence: `backend/server.js` imports `cors` but never calls
	 `app.use(cors())` or configures an allowed origin.
	 Expected behavior: A browser page served by Vite on port 5173 can call the
	 backend on port 3000.
	 Current behavior: Browser requests may be blocked by CORS even though the
	 API helper uses the backend's actual port.
	 Suggested next action: Register CORS middleware before the task routes and
	 test a browser GET from the Vite app.

2. Problem: The custom error handler is disconnected.
	 Evidence: `backend/middleware/errorHandler.js` exists, but
	 `backend/server.js` never imports or mounts it after the routes.
	 Expected behavior: Route/database failures produce the documented JSON 500
	 response.
	 Current behavior: Express's default error handling is used instead, and
	 error behavior may differ from the intended response.
	 Suggested next action: Mount the handler after `app.use("/tasks", taskRoutes)`
	 and exercise invalid or failing requests.

3. Problem: The frontend only implements task retrieval in the UI.
	 Evidence: `pr1/src/pages/Projects.jsx` imports only `getTasks`; it has no
	 form or mutation handlers. `createTask`, `updateTask`, and `deleteTask` are
	 unused in `pr1/src/api.jsx`.
	 Expected behavior: A user can create, view, update, and delete tasks from
	 React.
	 Current behavior: Existing tasks can be displayed if the GET succeeds, but
	 all CRUD mutations require an external client or direct API request.
	 Suggested next action: Add task form/list controls and connect the three
	 existing mutation helpers, then refresh or update local state after each
	 successful mutation.

4. Problem: The practical handout and code specify different backend ports.
	 Evidence: The handout says 5000, while `backend/server.js` and
	 `pr1/src/api.jsx` both use 3000. `pr1/vite.config.js` has no port override.
	 Expected behavior: Frontend and backend use one documented, reachable port.
	 Current behavior: The current code is internally aligned on 3000, but any
	 instruction or test expecting 5000 will fail.
	 Suggested next action: Decide whether 3000 or 5000 is the required contract;
	 then update the API base URL and server port together if needed. Do not
	 assume 5000 based only on the handout.

5. Problem: Backend runtime and MongoDB connectivity are unverified.
	 Evidence: `connectDB()` depends on `MONGO_URI` and exits the process on
	 connection failure; no runtime request test or MongoDB status is recorded
	 in the repository.
	 Expected behavior: The backend starts, connects to the local
	 `task_management` database, and serves `/tasks`.
	 Current behavior: Source code is present, but actual startup, connection,
	 and persistence have not been verified here.
	 Suggested next action: Start MongoDB, start the backend from `backend/`,
	 check its connection/startup logs, and exercise all four endpoints.

6. Problem: Validation and error responses are minimal.
	 Evidence: POST passes the entire request body to `Task.create`, and the
	 generic error handler returns only a 500 message. There is no explicit
	 malformed-id or validation response mapping.
	 Expected behavior: Invalid task input and ids produce useful predictable
	 API errors.
	 Current behavior: Required-field validation is delegated to Mongoose, while
	 malformed ids and other errors are forwarded without a mounted custom
	 handler.
	 Suggested next action: Verify the actual error responses during API tests;
	 add validation/error handling only as required by the practical.

7. Problem: Mutation refresh behavior is absent from the UI.
	 Evidence: The current Projects page performs its GET only on initial mount
	 and has no mutation handlers.
	 Expected behavior: The visible list reflects successful create, update, and
	 delete operations without requiring a manual page reload.
	 Current behavior: No UI mutation can currently occur, so no re-fetch or
	 local-state update occurs.
	 Suggested next action: Re-fetch tasks or update state after each successful
	 mutation and surface mutation loading/error states.
